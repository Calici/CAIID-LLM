# Google but Drug Discovery
## 1. Specs
### A. API Integration For The Following Data Sources
- Pubmed
- Europe PMC
- PubChem
- Clinical Trials
- Chembl
- OpenFDA
- NCBI
- OpenTargets
### B. Simple Local Filesystem
A simple local filesystem that is accessible and readable through a large language model. However, this model, shall never under any circumstances, have write access to this local filesystem. This local filesystem should be under managed under the user and user alone. Shall have no subdirectories and only files. Shall have a database managing summaries for every file uploaded, summary of which can be generated by the user or by the use of a language model. 
### C. Application UI
The application UI shall consist of a workspace which name could be unique or non-unique. The name of the workspace can be created by the user or inferred by a language model if not given. At any given time, a workspace consists of the following elements: 
#### 1. The Workspaces Pane
This shall consist of a list of other workspaces which name can be edited. 
#### 2. The Chat Panel
This is the chatting window that the user will see at all times. The chatting window is used to talk to a language model that can modify all other UI elements. 
#### 3. The Query Panel
This shall consists of a keyword panel, a fixed result panee of 10 entries, source selection. Keywords can be comma separated or be done with a separate UI. The result pane will change based on the keywords given. 
#### 4. The Local Filesystem
This will be a mini-drive the user can add files into.

## 2. System Design

#### I. Local Filesystem
```SQL
CREATE TABLE files (
    name TEXT NOT NULL UNIQUE,
    summary TEXT NOT NULL,
    create_date TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_modified TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    uuid TEXT NOT NULL UNIQUE PRIMARY KEY,
) STRICT;
```
#### II. Temporary File Uploads
```SQL
CREATE TABLE temp_files (
    name TEXT NOT NULL

    create_date TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_modified TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    uuid TEXT NOT NULL UNIQUE PRIMARY KEY
) STRICT;
```
#### III. Chat Workspace
```SQL
CREATE TABLE workspaces (
    name TEXT NOT NULL,
    create_date TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_modified TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    chat_history BLOB NOT NULL,
    uuid TEXT NOT NULL UNIQUE PRIMARY KEY
) STRICT;
```
#### IV. Server Configuration
```
CREATE TABLE configs (
  name TEXT NOT NULL UNIQUE,
  value TEXT NOT NULL
) STRICT;
```

#### II. Workspace
Before starting on the topic of workspace management, let's first define the chatting data type since this is a complex data structure that will need to be parsed and handled in a different way. 
- Chat History Structure
```ts
/* Message History Structure */
type UserMessageT = {
  type: "user", content: string
}
type ModelMessageT = {
  type: "ai", content: string
}
type ToolCallT = {
  type: "tool_call", tool_name: string, tool_id: string, tool_call_id: string, is_complete: boolean
}

/* This defines the messages that the model will send. I.e. returned from the SSE event */
type ModelResponseT = ModelMessageT | ToolCallT

/* This defines the whole structure */
type MessageT = UserMessageT | ModelMessageT | ToolCallT
type HistoryT = MessageT[]

/* Workspace State */
type StateT = {
  messages: MessageT[]
  queries: {
    title: str,
    source: str,
    abstract: Optional<str>,
    authors: str[],
    doi: Optional<str>
  }[]
}

```
- [GET] `workspace/<workspace_uuid>`
Return all the specifics of a workspace.
```ts
{
  name: string,
  uuid: string,
  chat_history: MessageT[],
  last_modified: datestring,
  create_date: datestring
}
```
- [POST] `workspace.chat`
Sends a chat. This is meant to be an SSE event backend where each GET request will stream the following until completion. 
```ts
{
  user_prompt: string,
  uuid: Option<str>
}
````
Returning as SSE:
```ts
{
  type: "chat",
  content: MessageT
} | {
  type: "record",
  content: {
    name: string,
    uuid: string,
    chat_history: StateT,
    last_modified: datestring,
    create_date: datestring
  } | {
    type: "query"
      content: {
      title: str,
      source: str,
      abstract: Optional<str>,
      authors: str[],
      doi: Optional<str>
    }[]
  }
}
```
The following care have to be taken to handle the SSE Event:
- stitch every `ModelMessageT` until either a `tool_call` or a `ModelEndResponseT` is made. Once a `ModelEndResponseT` is given, this implies that the SSE can be closed. 
- When a `tool_call` is made, it will be given in an undone state, once the `tool_call` is done, it will be updated with the same call to acknowledge it. It is guaranteed that the `tool_call` will either complete or not be added into the history. `tool_call` can be matched with `tool_call_id`. 

#### II. Filesystem Management
- [POST] `fs.temp_upload`
Upload a new file into the filesystem. 
```ts
{
  name: string,
  summary: Option<string>,
  file: File
}
```
Returns
```ts
{
  uuid: string
}
```

- [POST] `fs.confirm_upload/<temp_file_uuid>`
This confirms a previously temporary uploaded file. 
```ts
{
  name: string,
  summary: string
}
```
Returns 
```ts
{
  name: string,
  summary: string,
  uuid: string,
  create_date: datestring,
  last_modified: datestring
}
```
On name conflicts, this will return a 400 error. 
If file_uuid is not found, this will return a 404.

- [GET] `fs.ls`
Gets a list of all the files.
```ts
{
  name: string, summary: string, uuid: string
}[]
```

- [GET] `fs.download_file/<file_uuid>`
This will let the user download the file.
